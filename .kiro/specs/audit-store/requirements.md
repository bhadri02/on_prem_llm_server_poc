# Requirements Document

## Introduction

The Audit Store is the centralized, append-only audit trail service for the Enterprise On-Premises LLM Platform. It records every significant event generated by all processing layers (API Gateway, Security, Router, Cache, Inference, and Agent Framework) across the full request lifecycle — from first receipt through final response delivery.

This POC implementation uses FastAPI and SQLite to prove that every platform request produces a complete, queryable audit trail. It exposes a write API for fire-and-forget event ingestion from all layers, and a query API that lets operators trace the full lifecycle of any individual request. The service runs on port 9200, exposes Prometheus metrics on port 9090, and emits structured JSON logs to stdout.

Out of scope for this POC: hash chaining, S3/MinIO archival, GDPR erasure, compliance reports, Elasticsearch/ClickHouse backend, Index Lifecycle Management (ILM), role-based access control for auditors, HashiCorp Vault secret management, and mTLS.

## Glossary

- **Audit_Store**: The FastAPI service that persists and serves audit event records; runs on port 9200.
- **Audit_Event**: A single immutable record describing one significant action at one platform layer for one request.
- **Audit_DB**: The SQLite database file (default path `/data/audit.db`) that persists all Audit_Events.
- **Write_API**: The set of POST endpoints (`/audit/events`, `/audit/events/batch`) used by layers to ingest Audit_Events.
- **Query_API**: The set of GET endpoints used by operators to retrieve and summarize Audit_Events.
- **IMF**: Internal Message Format — the canonical JSON envelope defined in the platform master contract that all inter-layer messages must use.
- **request_id**: The UUID-v4 field present in every IMF message and every Audit_Event that correlates all events belonging to a single end-to-end request.
- **Layer**: One of the enumerated platform processing stages: `api_gateway`, `security`, `router`, `cache`, `inference`, `agent`.
- **Event_Type**: One of the enumerated action labels: `request_received`, `auth_pass`, `auth_fail`, `security_block`, `cache_hit`, `inference_start`, `inference_complete`, `response_sent`.
- **Outcome**: One of the enumerated result codes: `pass`, `block`, `flag`.
- **Caller**: Any platform layer service that sends an HTTP POST to the Write_API.
- **Metrics_Endpoint**: The `/metrics` endpoint on port 9090 that exposes Prometheus metrics.
- **Batch**: A JSON array of one or more Audit_Event objects submitted in a single POST request.

## Requirements

### Requirement 1: Audit Event Write — Single Record

**User Story:** As a platform layer service, I want to POST a single audit event to the Audit Store so that every significant processing action is permanently recorded without blocking the main request flow.

#### Acceptance Criteria

1. WHEN a POST request is received at `/audit/events` with a JSON body containing all mandatory fields (`request_id`, `layer`, `event_type`, `outcome`), THE Audit_Store SHALL insert the record into Audit_DB within 200 ms and return HTTP 201 with the `audit_id` in the response body.
2. WHEN the `audit_id` field is absent from the request body, THE Audit_Store SHALL generate a UUID-v4 value and assign it to the inserted record before responding.
3. WHEN the `timestamp_utc` field is absent from the request body, THE Audit_Store SHALL assign the current UTC time in ISO-8601 format to the inserted record.
4. IF the `request_id` field is absent or not a valid UUID-v4, THEN THE Audit_Store SHALL return HTTP 422 with a structured error body identifying the failing field; validation errors SHALL take precedence over any concurrent SQLite errors.
5. IF the `layer` field is absent or contains a value not in the enumerated set (`api_gateway`, `security`, `router`, `cache`, `inference`, `agent`), THEN THE Audit_Store SHALL return HTTP 422 with a structured error body identifying the invalid value; validation errors SHALL take precedence over any concurrent SQLite errors.
6. IF the `event_type` field is absent or contains a value not in the enumerated set (`request_received`, `auth_pass`, `auth_fail`, `security_block`, `cache_hit`, `inference_start`, `inference_complete`, `response_sent`), THEN THE Audit_Store SHALL return HTTP 422 with a structured error body identifying the invalid value; validation errors SHALL take precedence over any concurrent SQLite errors.
7. IF the `outcome` field is absent or contains a value not in the enumerated set (`pass`, `block`, `flag`), THEN THE Audit_Store SHALL return HTTP 422 with a structured error body identifying the invalid value; validation errors SHALL take precedence over any concurrent SQLite errors.
8. IF the request body is not parseable as valid JSON, THEN THE Audit_Store SHALL return HTTP 400 with a structured error body indicating a malformed request; no insertion is attempted.
9. IF a SQLite write error occurs during insertion after all validations pass, THEN THE Audit_Store SHALL return HTTP 500 with a structured error body and emit a structured JSON error log to stdout; the Caller receives no partial data.
10. THE Audit_Store SHALL NOT expose a `PUT`, `PATCH`, or `DELETE` endpoint for audit events, preserving append-only semantics.

### Requirement 2: Audit Event Write — Batch Records

**User Story:** As a platform layer service, I want to POST multiple audit events in a single request to the Audit Store so that I can reduce network overhead during high-throughput processing.

#### Acceptance Criteria

1. WHEN a JSON array of one or more valid Audit_Event objects (maximum 500 records) is received at `POST /audit/events/batch`, THE Audit_Store SHALL insert all records into Audit_DB atomically, return HTTP 201 with a list of inserted `audit_id` values, and complete the full end-to-end response within 500 ms.
2. WHEN the batch array contains records where `audit_id` is absent, THE Audit_Store SHALL generate UUID-v4 values for each such record before insertion.
3. IF any single record in the batch fails schema validation (missing `request_id`, invalid `layer`, invalid `event_type`, invalid `outcome`), THEN THE Audit_Store SHALL reject the entire batch with HTTP 422, insert zero records, and return a structured error body identifying every failing record by its index in the array; partial insertion of valid records within the same batch is not permitted.
4. IF the batch array is empty, THEN THE Audit_Store SHALL return HTTP 422 with a message indicating the array must contain at least one record.
5. IF the batch array contains more than 500 records, THEN THE Audit_Store SHALL return HTTP 422 with a message indicating the maximum batch size is 500.
6. IF a SQLite write error occurs during batch insertion, THEN THE Audit_Store SHALL roll back the entire transaction, return HTTP 500, and emit a structured JSON error log to stdout.

### Requirement 3: Audit Query — Events by Request ID

**User Story:** As a platform operator, I want to retrieve all audit events associated with a specific `request_id` so that I can trace the complete lifecycle of any individual request across all platform layers.

#### Acceptance Criteria

1. WHEN a valid UUID-v4 is supplied as `{request_id}` in `GET /audit/requests/{request_id}`, THE Query_API SHALL return HTTP 200 with a JSON array of all Audit_Events matching that `request_id`, ordered by `timestamp_utc` ascending; when two or more events share the same `timestamp_utc`, they SHALL be secondarily ordered by `audit_id` ascending.
2. WHEN no events exist for the supplied `request_id` but the value is a valid UUID-v4, THE Query_API SHALL return HTTP 200 with an empty JSON array.
3. IF `{request_id}` is not a valid UUID-v4 format, THEN THE Query_API SHALL return HTTP 422 with a structured error body containing a `detail` field that identifies `request_id` as the failing parameter and states the expected format.
4. WHEN events are returned, THE Query_API SHALL deserialize the `pii_actions` and `policy_decisions` TEXT columns from their stored JSON string representation and include them as JSON arrays (not strings) in each returned Audit_Event object.
5. IF a stored `pii_actions` or `policy_decisions` value is not valid JSON at query time, THEN THE Query_API SHALL return the raw string value in that field rather than failing the request, and SHALL emit a WARNING-level log entry identifying the `audit_id` of the affected record.

### Requirement 4: Audit Query — Events by Filter

**User Story:** As a platform operator, I want to query audit events filtered by user, event type, and time range so that I can investigate activity patterns and incidents.

#### Acceptance Criteria

1. WHEN `GET /audit/events` is called with a `user_id` query parameter, THE Query_API SHALL return HTTP 200 with all Audit_Events where `user_id` exactly matches the parameter value, subject to the 1000-record limit.
2. WHEN `GET /audit/events` is called with a `from` query parameter containing a valid ISO-8601 UTC datetime string (ending in `Z` or `+00:00`), THE Query_API SHALL exclude all Audit_Events where `timestamp_utc` is strictly before the `from` value.
3. WHEN `GET /audit/events` is called with a `to` query parameter containing a valid ISO-8601 UTC datetime string (ending in `Z` or `+00:00`), THE Query_API SHALL exclude all Audit_Events where `timestamp_utc` is strictly after the `to` value.
4. WHEN `GET /audit/events` is called with an `event_type` query parameter, THE Query_API SHALL return only Audit_Events where `event_type` exactly matches the parameter value, subject to the 1000-record limit.
5. WHEN multiple filter parameters are provided simultaneously, THE Query_API SHALL apply all filters conjunctively (AND logic) and return only Audit_Events satisfying every condition, subject to the 1000-record limit.
6. WHEN any combination of filter parameters is provided (or none at all), THE Query_API SHALL return results ordered by `timestamp_utc` descending, limited to at most 1000 records.
7. IF the `from` or `to` parameter value is not a valid ISO-8601 UTC datetime string (missing `Z` or `+00:00` offset, or malformed), THEN THE Query_API SHALL return HTTP 422 with a structured error body that names each invalid parameter and states the required format.
8. IF the `from` parameter value is chronologically after the `to` parameter value, THEN THE Query_API SHALL return HTTP 422 with a structured error body indicating the range is invalid.
9. IF no records match the supplied filters, THE Query_API SHALL return HTTP 200 with an empty JSON array.
10. IF the `user_id` query parameter is present but its value is an empty string, THEN THE Query_API SHALL return HTTP 422 with a structured error body indicating that `user_id` must be a non-empty string.

### Requirement 5: Audit Query — Summary Statistics

**User Story:** As a platform operator, I want to retrieve aggregated counts of audit events grouped by outcome and layer so that I can quickly assess the overall health and activity distribution of the platform.

#### Acceptance Criteria

1. WHEN `GET /audit/summary` is called (with or without `from`/`to` parameters), THE Query_API SHALL return HTTP 200 with a JSON object containing: a `total_events` integer count, a `by_outcome` object mapping each outcome value to its event count, and a `by_layer` object mapping each layer value to its event count — all counts restricted to the specified time range when `from` and/or `to` are supplied.
2. WHEN `GET /audit/summary` is called with a `from` query parameter containing a valid ISO-8601 UTC datetime, THE Query_API SHALL restrict the aggregation to Audit_Events where `timestamp_utc` is greater than or equal to the `from` value.
3. WHEN `GET /audit/summary` is called with a `to` query parameter containing a valid ISO-8601 UTC datetime, THE Query_API SHALL restrict the aggregation to Audit_Events where `timestamp_utc` is less than or equal to the `to` value.
4. THE Query_API SHALL include a `total_events` count field at the top level of the summary response reflecting the total number of events matching the applied time range (or all events if no range is specified).
5. IF the `from` or `to` parameter value on any Query_API endpoint is not a valid ISO-8601 UTC datetime (i.e., it lacks a `Z` or `+00:00` suffix, or is otherwise malformed), THEN THE Query_API SHALL return HTTP 422 with a structured error body that names each invalid parameter.
6. IF `from` and `to` are both supplied and `from` is chronologically after `to`, THEN THE Query_API SHALL return HTTP 422 with a structured error body indicating the range is invalid.
7. WHEN no Audit_Events exist within the specified time range (or in the database if no range given), THE Query_API SHALL return HTTP 200 with `total_events: 0` and empty `by_outcome` and `by_layer` objects.

### Requirement 6: Health Check Endpoint

**User Story:** As a Kubernetes liveness probe, I want a lightweight health endpoint so that the orchestrator can detect when the Audit Store is unavailable.

#### Acceptance Criteria

1. WHEN `GET /health` is called and the Audit_Store successfully executes a probe query (e.g., `SELECT 1`) against Audit_DB within 200 ms, THE Audit_Store SHALL return HTTP 200 with a JSON body containing `{"status": "ok", "db": "connected"}`.
2. IF the Audit_DB probe query times out (exceeds 200 ms) or the connection is refused at the time of the health check, THEN THE Audit_Store SHALL return HTTP 503 with a JSON body containing `{"status": "degraded", "db": "unreachable"}`.
3. THE Audit_Store SHALL complete the `GET /health` response — including the DB probe — within 500 ms at the p95 percentile under normal operating conditions.
4. THE `GET /health` endpoint SHALL NOT require an `X-API-Key` header or any other authentication credential.

### Requirement 7: SQLite Storage and Schema

**User Story:** As the Audit Store service, I want a well-indexed SQLite schema so that common query patterns execute efficiently within the POC data volume.

#### Acceptance Criteria

1. WHEN the Audit_Store starts and the `audit_events` table does not already exist in Audit_DB, THE Audit_Store SHALL create the table with the following columns: `audit_id TEXT PRIMARY KEY`, `request_id TEXT NOT NULL`, `timestamp_utc TEXT NOT NULL`, `user_id TEXT`, `department TEXT`, `layer TEXT`, `event_type TEXT`, `model_used TEXT`, `prompt_tokens INTEGER DEFAULT 0`, `completion_tokens INTEGER DEFAULT 0`, `latency_ms INTEGER DEFAULT 0`, `outcome TEXT`, `error_code TEXT`, `pii_actions TEXT`, `policy_decisions TEXT`.
2. WHEN the Audit_Store starts and the indexes `idx_request_id`, `idx_user_id`, or `idx_timestamp` do not already exist on the `audit_events` table, THE Audit_Store SHALL create those indexes on the `request_id`, `user_id`, and `timestamp_utc` columns respectively.
3. THE Audit_Store SHALL serialize `pii_actions` and `policy_decisions` as JSON strings before writing to the TEXT columns, and deserialize them back to their native types when reading.
4. THE Audit_Store SHALL enforce `audit_id` as the PRIMARY KEY, ensuring no two records share the same `audit_id`; if a duplicate `audit_id` is submitted, THE Audit_Store SHALL return HTTP 409 with a structured error body.
5. IF the parent directory of the path specified by the `DB_PATH` environment variable does not exist, THEN THE Audit_Store SHALL log an ERROR message identifying the missing directory and refuse to start, exiting with a non-zero exit code.
6. IF the database file specified by `DB_PATH` does not exist but its parent directory does exist, THEN THE Audit_Store SHALL create the database file and initialize the schema on first startup.
7. WHEN the SQLite connection is established, THE Audit_Store SHALL immediately execute `PRAGMA journal_mode=WAL` so that read operations are not blocked while a write transaction is in progress.
8. IF the SQLite connection cannot be established during startup (e.g., file permission error), THEN THE Audit_Store SHALL log an ERROR message with the failure reason and refuse to start, exiting with a non-zero exit code.

### Requirement 8: Prometheus Metrics

**User Story:** As a platform SRE, I want the Audit Store to expose Prometheus metrics so that I can monitor write throughput and latency from the central observability stack.

#### Acceptance Criteria

1. THE Audit_Store SHALL expose a `/metrics` endpoint on port 9090 that returns a Prometheus text exposition format 0.0.4 response with `Content-Type: text/plain; version=0.0.4; charset=utf-8`.
2. THE Audit_Store SHALL increment the `llm_audit_writes_total` counter metric, labelled by `event_type` and `layer`, only after each audit event record is confirmed as successfully inserted into Audit_DB (one increment per record inserted; empty batches and validation failures do not increment the counter). Valid `event_type` label values are: `request_received`, `auth_pass`, `auth_fail`, `security_block`, `cache_hit`, `inference_start`, `inference_complete`, `response_sent`. Valid `layer` label values are: `api_gateway`, `security`, `router`, `cache`, `inference`, `agent`. If an event carries an out-of-enumeration value it SHALL be recorded with the label value `unknown`.
3. THE Audit_Store SHALL record the elapsed time from write handler entry to DB confirmation or error in the `llm_audit_write_latency_seconds` histogram metric, labelled by `event_type` and `layer`, using buckets at: 0.005, 0.01, 0.025, 0.05, 0.1, 0.25, 0.5, 1.0, 2.5 seconds; this measurement covers all write attempts including those that fail.
4. IF a write fails due to a validation or database error, THEN THE Audit_Store SHALL NOT increment `llm_audit_writes_total` for the failed records but SHALL still record the elapsed time in `llm_audit_write_latency_seconds`.

### Requirement 9: Structured JSON Logging

**User Story:** As a platform SRE, I want every significant Audit Store action logged as structured JSON to stdout so that log aggregation pipelines can index and query service activity.

#### Acceptance Criteria

1. THE Audit_Store SHALL emit all log entries as single-line JSON objects to stdout; no log entry SHALL span multiple lines.
2. WHEN an audit event is successfully written, THE Audit_Store SHALL emit a log entry at INFO level containing at minimum the fields: `audit_id`, `request_id`, `layer`, `event_type`, and `latency_ms`.
3. WHEN an audit write fails, THE Audit_Store SHALL emit a log entry at ERROR level containing at minimum the fields: `request_id` (if present in the request), `error` (the error message string), and `layer` (if determinable from the request).
4. THE Audit_Store SHALL include a `timestamp` field in ISO-8601 UTC format and a `level` field (one of `DEBUG`, `INFO`, `WARNING`, `ERROR`) in every log entry.
5. THE Audit_Store SHALL respect the `LOG_LEVEL` environment variable to set the minimum log level; valid values are `DEBUG`, `INFO`, `WARNING`, `ERROR`; log entries below the configured level SHALL NOT be emitted to stdout.
6. WHERE `LOG_LEVEL` is not set or is set to an unrecognized value, THE Audit_Store SHALL default to `INFO` level logging.

### Requirement 10: Static API Key Authentication

**User Story:** As the platform security boundary, I want the Audit Store Write API to require a static API key so that only authorized platform layer services can insert audit records.

#### Acceptance Criteria

1. WHEN a POST request to `/audit/events` or `/audit/events/batch` is received without an `X-API-Key` header, THE Audit_Store SHALL return HTTP 401 with a JSON error body containing an `error` field with the value `"missing_api_key"`.
2. WHEN a POST request is received with an `X-API-Key` header whose value does not match the configured key, THE Audit_Store SHALL return HTTP 403 with a JSON error body containing an `error` field with the value `"invalid_api_key"`.
3. WHEN a POST request is received with an `X-API-Key` header whose value matches the configured key, THE Audit_Store SHALL forward the request to the write handler and return the response produced by that handler.
4. WHEN the Audit_Store starts, THE Audit_Store SHALL read the `AUDIT_API_KEY` environment variable and complete key loading before accepting any incoming requests.
5. IF the `AUDIT_API_KEY` environment variable is not set or is set to an empty string at startup, THEN THE Audit_Store SHALL log an ERROR message identifying the missing variable and refuse to start, exiting with a non-zero exit code.
6. THE Query_API endpoints (all GET endpoints) SHALL NOT require an `X-API-Key` header, and SHALL process requests without checking for the header.

### Requirement 11: Helm Chart — `llm-platform/charts/audit-store/`

**User Story:** As a platform DevOps engineer, I want a Helm chart for the Audit Store so that it can be deployed consistently to any Kubernetes cluster that runs the platform.

#### Acceptance Criteria

1. THE Audit_Store Helm chart SHALL include the following files: `Chart.yaml`, `values.yaml`, `templates/deployment.yaml`, `templates/service.yaml`, `templates/networkpolicy.yaml`, `templates/servicemonitor.yaml`, `templates/_helpers.tpl`, and `README.md`.
2. THE `values.yaml` SHALL include the following default values: `replicaCount: 1`, `image.repository: registry.local/audit-store`, `image.tag: ""`, `image.pullPolicy: IfNotPresent`, `service.port: 9200`, `env.DB_PATH: "/data/audit.db"`, `env.LOG_LEVEL: "INFO"`, `persistence.enabled: true`, `persistence.size: 5Gi`, `resources.requests.cpu: "100m"`, `resources.requests.memory: "256Mi"`, `resources.limits.cpu: "500m"`, `resources.limits.memory: "512Mi"`, `observability.metrics.enabled: true`, `observability.metrics.port: 9090`, `vault.enabled: false`, and `autoscaling.enabled: false`.
3. IF `persistence.enabled` is `true`, THEN `templates/deployment.yaml` SHALL create a PersistentVolumeClaim and mount it at `/data` in the container so that the SQLite database file survives pod restarts.
4. THE `templates/service.yaml` SHALL expose port 9200 (ClusterIP) for the application API and port 9090 for the Prometheus metrics endpoint, using label selectors defined in `templates/_helpers.tpl` to bind to the correct pods.
5. THE `templates/networkpolicy.yaml` SHALL allow ingress to port 9200 from the following namespaces only: `llm-api-gateway`, `llm-security`, `llm-router`, `llm-cache`, `llm-inference`, `llm-agent-framework`, `llm-governance`; and SHALL allow ingress to port 9090 from the `llm-observability` namespace only; all other ingress SHALL be denied.
6. THE `templates/servicemonitor.yaml` SHALL configure Prometheus to scrape the `/metrics` endpoint on port 9090 at a 30-second interval.
7. THE `Chart.yaml` SHALL declare `name: audit-store`, `version: 0.1.0`, and `appVersion: "0.1.0"`.
8. IF `persistence.enabled` is `false`, THEN `templates/deployment.yaml` SHALL deploy without creating or mounting a PersistentVolumeClaim; this configuration is permitted for testing or temporary deployments where audit data loss on pod restart is acceptable.
